# Feature Specification: AI健康咨询

**Feature Branch**: `005-ai-health-consultation`

**Created**: 2026-11-08

**Status**: Draft

**Input**: User description: "为患者开发一个健康咨询智能体，患者在主页进入 AI 健康咨询时，可以与患者进行医学方面的问答，问答时可参考患者的就诊信息与医学知识库（Why）；目标用户为患者（Who）；核心功能包括日常健康咨询（用药建议、康复指导）、紧急症状预警（显著信息预警 + 按患者上下文自动推送挂号弹窗）、多轮对话交互与多对话管理（What）"

**功能命名（原则 V 锁定）**：本功能名称自本规约起固定为 **「AI健康咨询」**，代码与界面标识统一使用 `ai-health-consultation` / `AI健康咨询`，后续阶段不得再改为「健康科普」「AI健康资讯」等名称。

## Clarifications

### Session 2026-11-08

- Q: 紧急症状的判定机制采用哪种？ → A: **规则优先 + 模型复核**：先用可维护的症状关键词/规则表命中，再由模型确认并生成可解释文案；召回靠规则兜底，误报靠模型收敛。
- Q: 智能体回答的输出方式？ → A: **流式输出（SSE）**：逐字返回，缩短首字时延；契约需定义事件类型与中断降级。
- Q: 医学知识库怎么落地？ → A: **复用 002 的科室-疾病知识库**（只读，不新增表）；其面向「导诊匹配科室」，对用药与康复指导的覆盖缺口由 `plan.md` 评估，不在本规约新增知识表。
- Q: 患者对话历史的保留策略？ → A: **长期保留 + 患者可手动清空**：满足刷新/重登恢复，并为患者提供「清空全部历史」入口（需审计）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 多轮医学问答（参考我的就诊信息） (Priority: P1)

已登录患者在首页点击「AI健康咨询」进入对话页，直接输入问题（如「我这两天咳嗽有痰，之前开的阿莫西林还能吃吗」）。智能体结合该患者既往问诊记录与处方信息，给出用药建议与康复指导，并以追问、补充说明的方式完成多轮交流；每轮回答末尾显示医学免责声明。

**Why this priority**: 这是患者使用本功能的第一诉求；没有可用的问答闭环，其余功能（预警、多对话）都无从承载。

**Independent Test**: 以一名有历史问诊记录的患者登录，发起一次会话并连续提问 3 轮，检查回答与免责声明；再以无任何就诊记录的新患者重复，验证仍能给出通用建议且提示「暂无历史就诊信息」。

**Acceptance Scenarios**:

1. **Given** 患者已登录且有历史问诊/处方记录, **When** 患者进入 AI 健康咨询并提问, **Then** 系统返回医学建议，回答中引用的既往就诊信息与患者真实记录一致，且回答含免责声明
2. **Given** 患者已登录且无任何就诊记录, **When** 患者提问, **Then** 系统给出通用健康建议，并明确提示「暂无历史就诊信息，建议仅供参考」
3. **Given** 患者处于同一会话中, **When** 患者连续追问且未重复上下文（如「那剂量呢」）, **Then** 系统能依据本会话前文正确理解指代并回答
4. **Given** 患者提问涉及具体用药剂量或处方调整, **When** 系统回答, **Then** 回答不得直接给出处方性结论，须引导患者复诊或咨询医生

---

### User Story 2 - 紧急症状预警与挂号引导 (Priority: P2)

患者在对话中描述紧急症状（如「胸口疼得厉害，喘不上气」），系统在回答顶部以醒目的紧急提示条预警（建议立即拨打 120 / 就近急诊），同时根据患者上下文自动弹出挂号引导弹窗，预填科室与患者信息，患者可直接进入挂号流程。

**Why this priority**: 直接关系患者安全，属于必须存在的风险兜底；但它依赖 US1 的对话通道，故排在 P1 之后。

**Independent Test**: 在对话中输入明确的紧急症状，验证页面出现紧急提示条、弹窗自动弹出且科室预填；再输入普通症状，验证不触发任何预警与弹窗。

**Acceptance Scenarios**:

1. **Given** 患者在对话中描述紧急症状, **When** 系统识别为紧急情况, **Then** 回答区域顶部出现高对比度紧急提示条，文案包含「立即就医/拨打 120」指引
2. **Given** 紧急情况已识别, **When** 预警展示, **Then** 自动弹出挂号引导弹窗，科室依据本次对话内容与患者历史信息预填，患者可一键跳转挂号
3. **Given** 患者关闭了挂号弹窗, **When** 患者继续对话, **Then** 紧急提示条仍然保留，患者可随时从提示条重新打开挂号入口
4. **Given** 患者描述的是普通不适（如「有点困」）, **When** 系统判断, **Then** 不出现紧急提示条、不弹出挂号弹窗
5. **Given** 症状规则命中但模型复核否决, **When** 系统输出回答, **Then** 不展示紧急提示条，但判定记录留痕，便于后续优化规则

---

### User Story 3 - 多对话管理 (Priority: P3)

患者可在左侧（PC）/抽屉（手机）中查看历史会话列表，新建对话、切换会话继续追问、重命名与会话删除；列表按最近活跃时间倒序展示，并显示会话标题与最后一条消息摘要。

**Why this priority**: 提升长期使用体验，但单会话已可满足核心诉求，故为 P3。

**Independent Test**: 新建 2 个会话分别提问不同主题，刷新页面后仍能看到两个会话及其历史消息，切换会话时上下文互不串扰。

**Acceptance Scenarios**:

1. **Given** 患者已存在多个会话, **When** 患者刷新或重新登录, **Then** 会话列表与各自消息历史完整恢复，顺序为最近活跃倒序
2. **Given** 患者在会话 A 提问, **When** 切换到会话 B 继续提问, **Then** B 的回答不受 A 上下文影响
3. **Given** 患者删除某会话, **When** 确认删除, **Then** 该会话及其消息从列表消失，且再次访问该会话地址返回「会话不存在」
4. **Given** 患者点击新建对话, **When** 会话创建完成, **Then** 进入空白会话，历史会话仍保留在列表中

---

### Edge Cases

- 患者单条输入超长（如粘贴整段病历上万字）时的处理与提示。
- AI 服务超时、限流或不可用时的降级表现（不得吞掉患者消息、不得伪造回答）。
- 患者在一次提问中同时包含紧急症状与普通咨询时，预警优先级如何体现。
- 患者用「多标签页」同时打开同一会话并发发送消息时，消息顺序与重复请求的处理。
- 会话被删除后，另一个标签页仍向其发送消息的处理。
- 患者越权访问他人会话（改动 URL 或会话号）的处理。
- 紧急症状误判（过度预警）与漏判（该预警未预警）的兜底与人工反馈渠道。
- 患者输入与医疗无关的内容（闲聊、越界请求）时的回答边界。
- 患者未完成实名认证/未登录时访问该功能的处理。
- 会话轮次过多导致上下文超长时的截断策略与提示。
- 规则命中紧急症状但模型复核否决时的表现（不预警、不弹窗，但须留判定日志）。
- 流式输出中途断开（网络抖动、服务重启、患者主动停止）后，已生成内容与重试入口的表现。
- 患者在一个标签页清空全部历史时，另一个标签页仍在查看旧会话的处理。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 患者 MUST 能从首页进入「AI健康咨询」；未登录 MUST 先登录并回跳原页面
- **FR-002**: 系统 MUST 支持患者与智能体的多轮问答，同一会话内多轮问答须保持上下文连贯
- **FR-003**: 系统 MUST 在回答中参考该患者的既往就诊信息（问诊记录、处方、过敏/注意事项等），且仅可引用属于该患者的数据
- **FR-004**: 系统 MUST 在回答中参考医学知识库内容（只读复用 002 的科室-疾病知识库）；知识库未覆盖时 MUST 明确说明依据有限，不得编造来源
- **FR-005**: 系统 MUST 对每条回答附加医学免责声明，声明不替代医生面诊
- **FR-006**: 系统 MUST 在识别到紧急症状时，在回答区域顶部展示高对比度紧急预警信息（含立即就医/拨打 120 指引）
- **FR-007**: 系统 MUST 在紧急预警触发时自动弹出挂号引导弹窗，并按本次对话内容与患者上下文预填科室
- **FR-008**: 患者 MUST 能关闭弹窗后仍通过预警区域重新打开挂号入口
- **FR-009**: 患者 MUST 能新建对话；新建后 MUST 进入空白会话并保留历史会话
- **FR-010**: 患者 MUST 能查看自己的会话列表（最近活跃倒序），并能切换、重命名、删除会话
- **FR-011**: 系统 MUST 保证会话与消息的归属隔离：患者仅能读写自己的会话，越权访问 MUST 返回「不存在」类错误
- **FR-012**: 系统 MUST 在 AI 服务超时/不可用时降级处理：保留患者消息、给出可重试提示，禁止返回伪造的医学结论
- **FR-013**: 系统 MUST 对患者输入长度、消息条数与上下文长度设上限，超限时给出明确提示而非静默截断
- **FR-014**: 系统 MUST 记录本功能相关安全审计事件（如越权访问、异常调用），审计内容禁止包含完整病情描述等敏感明文
- **FR-015**: 系统 MUST 在患者描述用药剂量、处方调整等请求时，输出「建议复诊/咨询医生」的引导，不得给出可直接执行的处方结论
- **FR-016**: 系统 MUST 支持手机与 PC 双端使用（手机为抽屉式会话列表，PC 为侧栏）
- **FR-017**: 会话历史 MUST 长期保留，并在刷新与重新登录后恢复；患者 MUST 能手动清空自己的全部历史，清空后不可恢复且需写审计
- **FR-018**: 紧急症状判定 MUST 采用「规则优先 + 模型复核」：先由可维护的症状规则表命中，再由模型确认并生成触发原因说明；规则命中但模型否决或反之的情况 MUST 记入判定日志（不含病情明文）
- **FR-019**: 系统 MUST 以流式方式（SSE）返回回答内容，并定义可区分的事件（正文增量、紧急预警、结束、错误）；流式中断时 MUST 保留已生成内容并提供重试入口，禁止丢弃患者已发送的消息
- **FR-020**: 系统 MUST 在 AI 流式输出不可用或中途失败时，以明确错误事件结束本次回答，不得以空白或截断内容冒充完整回答

### Key Entities *(include if feature involves data)*

- **咨询会话（AI Consultation Session）**: 一次连续对话的容器。关键属性：所属患者、标题、最近活跃时间、消息数量、状态（进行中/已删除）。一患者可有多个会话，会话之间上下文隔离。
- **咨询消息（AI Consultation Message）**: 会话中的一条发言。关键属性：所属会话、角色（患者/助手）、内容、发生时间、是否触发紧急预警、关联的挂号引导信息（科室等）。
- **就诊信息引用（Consultation Reference）**: 回答所依据的患者历史信息（问诊记录/处方/注意事项）的引用关系，用于可追溯与合规说明，不复制原始病历全文。
- **医学知识库条目（Medical Knowledge Entry）**: 回答所依据的医学知识（症状、常见处置、用药注意等）。本功能**只读复用 002 的科室-疾病知识库**（`department_disease_kb`），不新增知识表；其覆盖面缺口在 `plan.md` 评估，枚举与字段以 002 的 `data-model.md` 为唯一来源。
- **紧急判定记录（Emergency Decision Log）**: 一次紧急判定的留痕。关键属性：会话/消息、命中规则标识、模型复核结论、是否最终预警、时间。用于 SC-008 的可回溯，不保存病情明文。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 患者从首页进入并完成首次提问不超过 3 次点击；因采用流式输出，从发送到出现首个可见字符 ≤ 1.5 秒（AI 未响应时须先出现明确的「思考中」状态，不得空白等待）
- **SC-002**: 在 50 条预置医学问题的验收集上，回答包含免责声明的比例为 100%，引用就诊信息与患者本人记录的一致率 100%
- **SC-003**: 在 20 条预置紧急症状样本上，预警召回率 100%（宁可过度预警，不可漏判）；在 20 条普通症状样本上，误报率 ≤ 10%
- **SC-004**: 患者越权访问他人会话的成功率为 0（全部返回「不存在」类错误）
- **SC-005**: AI 服务不可用时，100% 的请求得到可理解的降级提示，0 例返回伪造医学结论
- **SC-006**: 多会话场景下，切换会话后上下文串扰为 0 例
- **SC-007**: 会话与消息在刷新页面、重新登录后恢复成功率 100%
- **SC-008**: 紧急判定链路（规则命中/未命中、模型确认/否决）留痕率 100%，任意一次预警均可在判定日志中回溯到触发规则与复核结论
- **SC-009**: 流式输出中断时，100% 的请求保留已生成内容并显示重试入口，0 例静默丢弃患者消息
- **SC-010**: 患者清空全部历史后，会话列表与消息在 1 次刷新内变为空，且无法通过任何入口恢复

## Assumptions

- 患者账号与登录体系沿用 001 已有能力；本功能不新增注册/登录流程。
- 就诊信息来自 002 问诊记录与 003 电子处方，本功能仅只读引用，不修改其数据。
- 紧急预警为「提示与引导」，不构成诊断；最终是否就医由患者决定。
- 挂号跳转复用 002 已有预约挂号流程（科室/医生/时段选择）。
- AI 模型调用沿用系统既有的模型接入方式（宪法「解释与待决项」中 DeepSeek 调用形态待 plan 阶段确认，本规约不实现两套链路）。
- 医学知识库以 002 的科室-疾病知识库为基线（只读复用），本功能不承担知识库内容的生产与医学审核责任；覆盖面缺口在 plan 阶段评估，必要时另立功能补齐。
- 紧急判定为「规则优先 + 模型复核」两级链路，规则表由产品与医学顾问共同维护，模型仅用于确认与生成解释文案。
- 对话历史长期保留，患者可自行清空；不设自动过期清理（如需满足更严格的数据最小化要求，由合规评审另行提出）。
- 患者历史就诊信息为空属于正常场景，系统退化为通用健康建议。

## Constitution Alignment *(mandatory)*

依 `.specify/memory/constitution.md`（v1.0.0）：

- 涉及 API 的功能需求必须引用 `specs/005-ai-health-consultation/contracts/` 中的请求/响应结构，禁止推测字段（原则 III）。
- 涉及状态枚举的需求必须引用 `specs/005-ai-health-consultation/data-model.md` 中的枚举定义，禁止硬编码（原则 II / III）。
- Edge Cases 与 Spec 阶段 checklist 中识别的风险项须逐条映射为测试用例（AI 超时、超长输入、多 Tab 并发、删除后发送、越权访问等），见原则 VI。
- 功能命名在规约阶段一次确定（「AI健康咨询」），后续阶段不得反复改名（原则 V）。
- 前端 MUST 使用 `patientRequest` 独立实例，路由词干不得与 `/consultation/*` 冲突；对话页建议使用独立词干 `/health-consultation`，最终以 `plan.md` 为准（原则 II）。
- 患者身份提取 MUST 复用 `PatientIdExtractor`，Controller 不得自行解析令牌（原则 II）。
- 审计与日志禁止出现完整病情明文、手机号、身份证号（原则 IV）。
- 医学免责声明、「不得给出处方性结论」属于安全边界，须在契约与测试用例中体现（原则 III / VI）。

## Out of Scope

- 智能体替代医生诊断、开具处方或修改既有处方。
- 图文/语音多模态问诊（本期仅文本对话）。
- 医生端查看患者 AI 咨询记录的运营后台。
- 医学知识库的录入、审核与版本管理界面。
