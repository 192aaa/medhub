# 功能规约：处方取药

**功能分支**：`004-prescription-dispensing`

**创建日期**：2026-11-08

**状态**：草稿（已经 2026-11-08 `/speckit.clarify` 确认 Q1–Q7 定稿，结论见第 9 节）

**输入**：用户描述：「为药店工作人员提供电子处方查验功能，使其可以根据患者提供的电子处方进行取药，并通过二维码进行处方验真。患者通过电子处方取药；药店工作人员通过电子处方拿药。处方二维码展示：患者可以查看与展示电子处方信息，处方信息中包含验真二维码，以供药店店员获取处方信息。电子处方验真：药店人员登录系统后，可以通过扫码方式验证处方的真实性，并且查看到当前的电子处方的状态（未取药/已取药/已过期），同时也可以将未取药的状态更新为已取药。」

**功能命名（冻结）**：中文功能名固定为「处方取药」；英文标识固定为 `prescription-dispensing`；前端页面名固定为「我的处方」「处方详情」「药店登录」「处方验真」「取药核销」。依据宪法原则 V，本规约阶段一次确定，后续 `/speckit.plan`、`/speckit.tasks`、`/speckit.implement` 及前端开发不得反复改名。

## 1. 背景与目标

`003-doctor-consultation` 已实现医生开具电子处方：处方经服务端私钥签名，带水印与验真二维码，二维码内容为验真链接（处方号 + 签名摘要），默认有效期 3 天；但 003 明确将「处方下游（药房核销、购药）」划在范围之外，`PrescriptionStatus` 目前只有「草稿 / 已签名 / 已过期 / 已作废」，且二维码指向的验真页面与药店角色尚未实现。

本功能承接该范围外能力，补齐电子处方从「医生开具」到「患者取药」的最后一环：

- 患者侧：可查看本人全部已签名电子处方，并在到店时向药店出示含验真二维码的处方页面。
- 药店侧：药店工作人员登录后扫码验真，确认处方真实、有效、未被取药，并可将「未取药」核销为「已取药」。

目标是让「一张电子处方只能被取药一次」这件事在系统内可验证、可追溯、不可抵赖；药品收费、医保结算、购药下单、配送与退药不在本规约范围。

## 2. 目标用户

- **患者**：已通过 `001-patient-identity` 实名认证、经 `002-appointment-consultation` + `003-doctor-consultation` 获得已签名电子处方；需要查看并出示处方（含验真二维码）以便到店取药。
- **药店工作人员**：由管理员/运维预置账号并启用的药店从业人员；需要登录药店端，扫码验真处方、查看取药状态，并对未取药处方执行取药核销。

本规约不覆盖：药店账号自助注册与管理员建号界面、药店入驻与资质审核、药品收费与医保结算、药品配送、部分取药、撤销核销与退药、药店端取药记录查询（见第 8 节 FR-023 与第 9 节 Q3、Q6）。

## 3. 用户场景与测试（必填）

用户故事按重要性排序，每个故事均可独立开发、独立测试、独立演示并单独交付价值。

### 用户故事 1 - 药店工作人员登录并扫码验真处方（优先级：P1）

药店工作人员使用预置账号登录药店端，用扫码设备/摄像头扫描患者出示的处方二维码（或在无扫码条件时手工输入处方号与签名摘要），系统校验二维码真伪后展示处方要素与当前取药状态（未取药 / 已取药 / 已过期 / 已作废），并明确告知是否可以取药。

**优先级理由**：验真是药店取药行为的合法性前提，也是本功能的唯一入口；没有它，后续核销无从谈起。仅交付本故事即可独立演示「扫码辨真伪」的价值。

**独立测试**：使用预置药店账号与一张已签名处方（含二维码），完成「登录 → 扫码 → 看到处方要素与状态」，并分别用篡改后的二维码、过期处方验证拒绝与状态展示，即可独立交付「可验真」的价值。

**验收场景**：

1. **假设** 药店账号有效且处方已签名未过期未被取药，**当** 扫码验真，**则** 展示处方号、药品清单、用法用量、开方医生、开方时间、有效期与「未取药」，并提示可以取药。
2. **假设** 二维码内容被篡改、签名摘要不匹配或处方号不存在，**当** 验真，**则** 返回统一失败提示，且不返回任何处方业务字段。
3. **假设** 处方已过期或已作废，**当** 验真，**则** 展示对应状态并明确提示不可取药。
4. **假设** 药店账号或密码错误、账号被禁用，**当** 登录，**则** 返回统一模糊失败提示，不泄漏账号是否存在。
5. **假设** 未登录或使用患者/医生身份访问药店端接口，**当** 发起请求，**则** 被拒绝且不返回任何处方资料。

---

### 用户故事 2 - 未取药处方核销为已取药（优先级：P1）

药店工作人员在验真结果页确认处方处于「未取药」且未过期、未作废后，点击「确认取药」，系统写入取药核销记录并将处方展示状态更新为「已取药」，记录核销时间与核销人；重复点击或多名店员同时操作时，只允许成功一次，核销不可回退。

**优先级理由**：核销是「一张处方只能取一次药」的落地动作，直接决定业务闭环是否成立；与验真共同构成最小可用产品。

**独立测试**：使用一张未取药处方，完成「验真 → 确认取药 → 状态变为已取药」，并验证重复核销、并发核销、过期处方核销均被拒绝，即可独立交付「可核销」的价值。

**验收场景**：

1. **假设** 处方展示状态为「未取药」且未过期未作废，**当** 店员确认取药，**则** 写入唯一核销记录，状态变为「已取药」，记录核销时间与核销人，并给出成功提示。
2. **假设** 同一处方被重复核销，**当** 再次确认取药，**则** 返回「已取药」且不产生第二条核销记录。
3. **假设** 两名店员并发核销同一处方，**当** 并发发生，**则** 仅一次成功，另一次返回「已取药」，不出现状态错乱。
4. **假设** 处方已过期、已作废或仍为草稿（未签名），**当** 尝试核销，**则** 被拒绝且处方状态不变。
5. **假设** 核销过程中数据库不可用，**当** 事务未提交，**则** 不产生「已取药」半成品状态，并返回统一降级提示。

---

### 用户故事 3 - 患者查看并出示处方与验真二维码（优先级：P2）

患者登录后进入「我的处方」查看本人全部已签名处方（含未取药 / 已取药 / 已过期 / 已作废，按开方时间倒序，草稿不展示），打开处方详情可看到处方要素、水印与验真二维码，到店时直接出示该页面供药店扫码。

**优先级理由**：二维码是验真的物理载体，但药店侧亦可手工输入处方号兜底，因此该故事可与 P1 故事解耦；缺少它时 P1 仍可演示，但真实取药体验不完整，故列为 P2。

**独立测试**：使用预置患者与已签名处方，完成「登录 → 我的处方 → 打开详情 → 展示二维码」，并验证他人处方不可见，即可独立交付「可出示处方」的价值。

**验收场景**：

1. **假设** 患者存在多张已签名处方，**当** 打开「我的处方」，**则** 按开方时间倒序看到全部处方（含处方号、开方医生、开方时间、有效期、状态），草稿处方不出现。
2. **假设** 患者打开处方详情，**当** 页面渲染，**则** 展示药品清单、用法用量、开方医生、有效期、水印与验真二维码。
3. **假设** 患者访问他人处方，**当** 发起请求，**则** 被拒绝且不返回任何处方内容。
4. **假设** 处方已过期或被作废，**当** 患者查看，**则** 明确展示对应状态且提示不可取药。
5. **假设** 患者未登录，**当** 访问处方页面，**则** 被引导至患者登录页，不展示任何处方信息。

## 4. 边界情况

- 二维码内容被篡改（改处方号、改签名摘要、截断、URL 编码变形、超长）时如何判定失败且不泄漏处方内容？
- 二维码被截图转发给第三方时如何处理？**已澄清**：处方不绑定药店，任一有效药店账号均可验真与核销，以「先核销成功者为准」，核销记录保存操作人以便追溯（Q2）。
- 处方不存在、处方号为非数字、签名摘要为空或含非法字符时如何处理？统一失败文案如何避免「处方是否存在」被枚举？
- 取药状态包含「未取药 / 已取药 / 已过期 / 已作废」，草稿（未签名）处方是否允许被验真或核销？**已澄清**：草稿处方一律不可验真成功、不可核销（FR-013）。
- 过期边界如何判定（`valid_until` 恰好等于当前时刻、超 1 秒、服务端与客户端时区差异）？
- 同一处方重复扫码、连续点击「确认取药」、两名店员并发核销时如何保证只成功一次？
- 核销请求已提交但响应丢失（网络中断）后，店员重试应看到什么结果？如何避免重复核销？
- 药店账号被禁用、登录过期、JWT 失效时验真/核销请求如何处理？
- 手工输入处方号场景如何防止暴力枚举？**已澄清**：MVP 不做限流，但全部失败须写审计事件并可统计，限流列入后续增强（Q4）。
- 患者端处方列表为空、处方明细为空、药品被下架或字段缺失时如何展示？
- 处方含患者姓名、诊断等敏感信息时，药店端展示与审计日志如何脱敏？药店端是否可见完整患者身份信息？
- 数据库、缓存不可用或超时时如何返回统一降级提示，并保证不产生半成品状态？
- 取药状态由核销记录派生时，若核销记录存在但处方已过期，展示状态如何取舍？**已澄清**：已取药优先于已过期（已取药为既成事实），已作废优先于未取药（Q5、FR-020）。
- 药店端是否提供取药记录查询？**已澄清**：本规约不提供，仅验真与核销两个动作（Q6、FR-023）。

## 5. 需求（必填）

### 5.1 功能需求

- **FR-001**：药店工作人员必须能使用管理员/运维预置的账号密码登录药店端；登录复用 001 统一认证体系并新增「药店」角色，失败返回统一模糊提示，不泄漏账号存在性；本规约不包含管理员建号界面。
- **FR-002**：药店端必须使用独立请求实例（`pharmacyRequest`）与独立 token 存储键，身份提取统一走 `PharmacyIdExtractor`，禁止与患者/医生端共用拦截器做角色判断。
- **FR-003**：患者必须能在「我的处方」查看本人全部已签名处方，含处方号、开方医生、开方时间、有效期与状态，按开方时间倒序返回；草稿处方不得出现。
- **FR-004**：患者处方详情必须展示处方要素（处方号、药品清单、规格、用法用量、开方医生、开方时间、有效期）与 003 已生成的处方水印。
- **FR-005**：患者处方详情必须展示验真二维码；二维码内容必须由服务端按 `data-model.md` 1.7 的 `v1` 令牌规则生成（加密处方 ID + 医院私钥签名），并与 003 处方签名规则**同源单一**（003 契约同步修订，禁止第二套二维码规则）；二维码中不得承载患者姓名、手机号、身份证号、诊断或药品明细等明文。
- **FR-006**：药店工作人员必须能在登录状态下通过扫码（摄像头/扫码枪）提交二维码内容发起验真；无扫码条件时必须支持手工输入处方号与签名摘要完成同等验真；不提供匿名公开验真入口。
- **FR-007**：验真必须校验签名摘要与处方存在性；校验失败必须返回统一失败提示，且响应中不得包含任何处方业务字段，避免被用于枚举处方。
- **FR-008**：验真成功必须返回取药所需处方要素与取药状态（未取药 / 已取药 / 已过期 / 已作废），并明确是否可取药；「已过期」与「已作废」均须以成功响应携带状态返回，不得用错误码代替状态展示（核销时仍按失败处理）。
- **FR-009**：取药状态与过期判定必须以服务端时间为准，不依赖客户端时间；过期判定基于处方有效期截止时刻。
- **FR-010**：药店工作人员必须能将「未取药」且未过期、未作废的处方核销为「已取药」，核销须记录核销时间与核销人（脱敏标识）；处方不绑定药店，任一有效药店账号均可核销，先核销成功者为准。
- **FR-011**：核销必须幂等：重复核销不得产生第二条核销记录，须返回「已取药」或首次结果。
- **FR-012**：同一处方的并发核销仅允许一次成功（核销记录唯一约束或条件写入保证），其余请求返回「已取药」，不得出现状态错乱。
- **FR-013**：核销为整单一次性动作，不支持部分取药、撤销或回退；已过期、已作废、未签名（草稿）处方不得核销。
- **FR-014**：患者只能查看本人处方；越权访问不得返回处方内容，且不得泄漏处方是否存在。
- **FR-015**：药店端不得展示患者完整手机号、身份证号；仅展示取药所必需的脱敏姓名与处方信息。
- **FR-016**：系统必须对验真、核销、验真失败、核销失败记录安全审计事件（含事件类型、结果、脱敏主体标识、TraceId），日志与响应禁止出现完整手机号、身份证号与处方敏感明文。
- **FR-017**：服务端必须对全部关键入参二次校验：处方号、签名摘要长度与字符集、状态枚举值、二维码解析结果；禁止仅依赖前端校验。
- **FR-018**：核销记录写入与审计事件写入必须在同一事务内编排，代码注释须标明关联表与流转路径；处方展示状态为派生值，不得额外落库。
- **FR-019**：内部依赖（数据库、缓存）不可用或超时时，必须返回统一降级提示（不泄漏连接串、堆栈或内部实现），且不得产生半成品记录。
- **FR-020**：处方取药状态必须由「取药核销记录 + 处方有效期 + 处方状态」统一派生，派生规则与状态枚举（未取药 / 已取药 / 已过期 / 已作废）定义在 `specs/004-prescription-dispensing/data-model.md`；不修改 003 已落库的 `PrescriptionStatus`，前后端禁止各自硬编码。
- **FR-021**：药店端接口必须拒绝患者/医生身份访问；患者端处方接口必须拒绝药店/医生身份访问，角色隔离由统一鉴权与独立请求实例共同保证。
- **FR-022**：验真与核销失败次数必须可通过审计事件统计，为后续限流与暴力枚举防护提供依据；MVP 不启用限流（列入后续增强）。
- **FR-023**：本规约药店端仅提供「处方验真」与「取药核销」两个动作，不提供取药记录列表、交接班对账或历史检索界面（后续迭代承接）。

### 5.2 关键实体

- **药店账号**：代表可登录药店端的从业人员账号；含登录凭证、启用状态与展示用脱敏标识，关联统一认证体系中的「药店」角色。
- **电子处方（复用 003）**：代表一张已签名处方；本功能只读其处方号、药品明细、开方医生、签名摘要、水印、有效期与状态，不修改其状态机。
- **处方药品明细（复用 003）**：代表处方中的一条药品条目（名称、规格、用法用量、注意事项），供药店核对发药。
- **取药核销记录（新增）**：代表一次取药事实；关联处方与核销药店账号，记录核销时间与结果，受「一处方最多一条记录」唯一性约束。
- **处方展示状态（派生）**：代表药店端与患者端共同展示的取药状态（未取药 / 已取药 / 已过期 / 已作废），由核销记录、有效期与处方状态按 `data-model.md` 规则派生，不单独落库。
- **处方验真请求**：代表一次扫码或手工输入验真；记录输入摘要、校验结果与时间，不存明文敏感信息。
- **安全审计事件（复用 001）**：代表验真、核销及失败尝试的留痕；含事件类型、结果、脱敏主体标识与 TraceId。

## 6. 成功标准（必填）

### 6.1 可度量结果

- **SC-001**：药店工作人员从扫码到看到验真结果的 P95 耗时不超过 2 秒。

## 7. 假设与澄清状态

### 7.1 已采用的假设

- 复用 `003-doctor-consultation` 的电子处方（签名、水印、二维码、默认 3 天有效期）作为唯一处方来源；本功能不重新实现开方与签名。

- 药店端请求实例 `pharmacyRequest` 已在 `web/src/api/request/pharmacy-request.ts` 预置，本功能直接沿用，不新建第二套请求封装。
- 取药为整单一次性核销；不支持部分取药、撤销核销与退药。
- 处方不绑定特定药店，任一有效药店账号均可验真与核销，先核销成功者为准。
- 取药状态不写入 003 的 `PrescriptionStatus`，改由「取药核销记录 + 有效期 + 处方状态」派生，派生规则与枚举集中在 `data-model.md`。
- 药店端本规约只提供验真与核销，不含取药记录查询与统计。
- 扫码由前端（浏览器摄像头或扫码枪键盘输入）完成，后端只接收二维码内容并独立校验签名，不信任前端解析结果。
- MVP 不启用验真失败限流，仅保证失败可审计、可统计。
- 药品收费、医保结算、购药下单、配送、退药均不在本规约范围。

## 8. 宪法对齐（必填）

依 `.specify/memory/constitution.md`（v1.0.0）：

- **功能命名冻结**：见文首「功能命名（冻结）」，后续阶段不得反复改名（原则 V）。
- **契约前置**：本功能需定义请求/响应结构的接口清单为「药店登录、处方验真、取药核销、患者处方列表、患者处方详情」共 5 个。字段结构由 `/speckit.plan` 阶段在 `specs/004-prescription-dispensing/contracts/` 产出；本规约不推测字段名、响应字段、`code` 取值或日期格式（原则 III）。前端 `src/api/` 类型与 Mock 数据必须标注该 contracts 路径并同步更新。
- **枚举唯一来源**：处方展示状态（未取药 / 已取药 / 已过期 / 已作废）、派生优先级规则、核销结果与新增 `ErrorCode` 须在 `specs/004-prescription-dispensing/data-model.md` 统一定义，并声明与 003 `PrescriptionStatus` 的映射关系；本规约只描述状态语义，禁止前后端各自硬编码（原则 II、III）。
- **安全约束**：药店与患者按角色隔离，处方签名验签在服务端完成，修改数据请求实施 `SameSite=Lax` + 双重 Cookie，统一模糊失败提示，业务异常文案统一由 `ErrorCode` 提供，审计日志脱敏，处方要素与金额由服务端确定；不提供匿名验真入口（原则 IV）。
- **分层与事务**：Controller → Service → Repository 严格分层；Service 对处方号、签名摘要、状态枚举二次校验；核销记录写入与状态派生的多表变更在同一事务内编排并注明关联表与流转路径（原则 II）。
- **路由与命名**：新路由须与既有 `/patient/*`、`/appointment/*`、`/consultation/*`、`/workbench/*`、`/system/*` 词干错开；`views/` 禁止直接调 axios，跨组件状态用 Pinia 且 store 从 `localStorage` 初始化；患者端与药店端请求实例相互独立（`patientRequest` / `pharmacyRequest`），身份提取统一用 `XxxIdExtractor`（原则 II、III）。
- **依赖治理**：不新增第三方运行时依赖；若确需二维码解析库，须在 `plan.md` 记录架构评审结论（原则 I）。
- **门禁复核**：`/speckit.plan` 必须复核 G1–G6 门禁，违规项登记到 `plan.md` 的 Complexity Tracking 表；未登记即阻断。
